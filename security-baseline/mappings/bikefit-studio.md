## Scope and profiles

| Profile             | Decision                          | Reason                                                                                                                         |
| ------------------- | --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| P1 Public site      | Selected                          | Public studio pages, booking form on `/afspraak`, cancel links by e-mail; visitors have no accounts                            |
| P2 Staff/admin      | Selected                          | CMS `/admin` with the roles admin, editor and provider (`src/lib/cms/permissions.ts:101-105`)                                  |
| P4 Non-web service  | Selected for the CLI scripts only | `db:migrate`, `cms:*` and the rollout tools run by hand against Neon (`package.json:19-29`); no API, worker or cron of its own |
| P3 Customer account | Not adopted: open decision D1     | Only the legacy webshop's Clerk accounts (`/account`, `/sign-in`, `/sign-up`) would qualify, if they stay reachable            |

The Level column is the strictest value across P1, P2 and P4
([Profile selection](../control-matrix.md#profile-selection)). IAM-08 (level – for all three) is kept
as an N/A row so that all 64 controls appear; the adoption guide would omit it. Not assessed:
`prototype/`, the hub page and the provider consoles (Vercel, Neon, Google, Resend, Clerk, Stripe).

### F2 — No MFA for any CMS role

- **Severity: High.** IAM-04, a MUST, is missing on an internet-facing back office that holds customer and health data; with the guessing allowance of F3, takeover needs modest effort.
- **Evidence:**
  - `src/lib/cms/auth.ts:159-168, 190-210`: the password is verified and the session issued at once; there is no second step.
  - `src/db/cms-schema.ts:86-101`: `cms_users` has no factor or recovery-code columns; no TOTP or WebAuthn code exists in `src/`.
  - All three roles are affected (`src/lib/cms/permissions.ts:101-105`). The bootstrap admin identifier is hard-coded (`scripts/cms-bootstrap.mts:40`), so the most valuable account name is predictable.
  - No account-security notifications: e-mail is sent only by the booking flow (`src/lib/booking/notifications.ts:168-218`).
- **Status basis:** observed in code.
- **Violated controls:** IAM-04, IAM-06, IAM-11; IAM-05 (SHOULD).
- **Acceptance criteria:**
  1. Every role completes TOTP (RFC 6238) or WebAuthn at every login, enforced server-side: a pending-MFA session reaches no `/admin` route and no repo function, and an account without a factor lands in enrolment; `cms:selftest` proves that `requireCmsUser` and `requirePermission` reject a pending session (AT-06).
  2. No SMS, voice or e-mail factor; TOTP ±1 step and single use; factor secrets AEAD-encrypted at rest (AT-06, AT-42).
  3. Ten recovery codes of at least 64 bits, stored hashed, single use, with notification and forced regeneration after use (AT-07).
  4. Second-factor failures count towards the IAM-09 throttle (AT-10).
  5. E-mail within 5 min for factor added or removed, password change or reset, recovery-code use and role elevation (AT-12); enrolment and removal audited (AT-50).
  6. WebAuthn offered to every account (IAM-05, AT-13; SHOULD).
- **Gate: G1** (IAM MUSTs; no open High finding). Project addition, stricter than the guide: also before any staff account beyond the owner is issued.

### F3 — Password verifier and guessing resistance below baseline

- **Severity: Medium; High while F2 is open.** IAM-02, IAM-03 and IAM-09 are partly met; without MFA the password is the only factor, so its strength and the throttle are the whole defence.
- **Evidence, policy and storage:**
  - `src/lib/cms/password.ts:31` `PASSWORD_MIN_LENGTH = 12`; `:42-43` lower-case, upper-case and digit rule; no blocklist in `:35-46`. The unit tests assert this rule (`src/lib/cms/password.test.ts:61-74`) and the docs repeat it (`docs/cms-architecture.md:192`; `docs/staging-runbook.md:191-192`).
  - `password.ts:27-28` scrypt `{ N: 2 ** 15, r: 8, p: 1 }` = 32 MiB (the comment says ~64 MB); IAM-03 needs N ≥ 2^17. The dummy hash uses the same cost (`auth.ts:81-88`).
  - No rehash at login (`auth.ts:194-210`).
- **Evidence, throttling:**
  - `src/lib/cms/auth.ts:43-44`: 10 failures per 15 min, about 960 guesses per account per day, indefinitely; no backoff, notification or ceiling.
  - `auth.ts:99` counts `email OR ip`: anyone can keep a known admin locked out.
  - `src/lib/cms/actions/auth.ts:27` and `auth.ts:184` fall back to the shared key `'unknown'`, against `src/lib/request-ip.ts:12-13`; the booking flow does it right (`src/lib/booking/public-booking.ts:252-255`).
  - Check and insert are not atomic (`auth.ts:186-199`): parallel attempts exceed the limit.
  - `changePassword` checks the current password without any throttle (`auth.ts:310`).
- **Status basis:** observed in code.
- **Violated controls:** IAM-02, IAM-03, IAM-09.
- **Acceptance criteria:**
  1. Minimum 15 characters (8 only once F2 makes MFA mandatory and unremovable), at least 64 accepted, no composition rules, a blocklist of at least 3,000 common passwords plus context words and a breached corpus, rejected with a reason; tests updated (AT-04).
  2. scrypt N ≥ 2^17, r = 8, p = 1 (or Argon2id m ≥ 19 MiB, t ≥ 2, p = 1); dummy hash at the same cost; weaker stored hashes re-hashed at the next successful login, with a test (AT-05); login timing still uniform (AT-11).
  3. Throttle per [identity-session.md](../identity-session.md#throttling): backoff per identifier and IP pair from the 6th failure, 1 s doubling to 15 min; more than 50 failures per IP in 15 min are refused for 15 min (a documented result, as login is a server action); notify at 20; password disabled until recovery at 100; no shared `'unknown'` key; failures from other sources do not lock the user out (AT-10).
  4. Atomic counting: `cms:selftest` fires 20 parallel wrong attempts and the count stays within the limit; `changePassword` failures count too.
  5. `docs/cms-architecture.md` §4 and `docs/staging-runbook.md` §6 updated.
- **Gate: G1**, with the same project addition as F2.

### F5 — Long-lived sessions without idle or absolute limit, `__Host-` prefix, step-up or self-service revocation

- **Severity: Medium.** The SES MUSTs are partly met: tokens are strong and HttpOnly, but a stolen or forgotten session stays valid for as long as it is used.
- **Evidence:**
  - `src/lib/cms/session.ts:26-28`: 14-day lifetime, renewal past the halfway point; `:118-126` renewal pushes the expiry out again, so a session used weekly never ends; no idle or absolute limit.
  - `session.ts:25` cookie name `cms_session` (no `__Host-`); `:183-191` HttpOnly, `secure: isProduction()`, SameSite=Lax, Path=/, `expires` 14 days.
  - User creation, password reset and role change need only a live admin session (`src/lib/cms/auth.ts:354-355, 395-396, 448-449`); a role change revokes no session and rotates no token (`auth.ts:448-463`).
  - The account page offers only "Afmelden op dit toestel" (`src/app/admin/(dashboard)/account/page.tsx:52-56`); `revokeOtherUserSessions` exists but is unused (`session.ts:144-156`).
- **Status basis:** observed in code; cookie attributes on the deployment need AT-15.
- **Violated controls:** SES-02, SES-03, SES-04, SES-05; SES-01 (no rotation at privilege change); WEB-06 (prefix).
- **Acceptance criteria:**
  1. Idle at most 30 min and absolute at most 12 h (P2), enforced server-side in `resolveSession` and tested with an injected clock (AT-17).
  2. `__Host-cms_session` with Secure, HttpOnly, Path=/, no Domain, SameSite Lax or Strict, and Max-Age no longer than the absolute lifetime (AT-14, AT-15).
  3. Re-authentication within the previous 5 min (password, plus the second factor once F2 lands) for credential, MFA and recovery-code changes, user and role management, password resets, and personal-data export or deletion (AT-18).
  4. Role and MFA changes revoke the user's other sessions and rotate the current token; users can end all their other sessions; admins can revoke a user's sessions (AT-16).
- **Gate: G1** (SES and WEB-06 MUSTs). Deferring an affected control past G1 needs a signed exception of at most 90 days for that control.

### F6 — No CSP; HSTS and COOP not set by the app; admin on the shared origin

- **Severity: Medium.** A defence-in-depth layer is missing. The sanitiser and React escaping hold today, but one origin serves the public site, the legacy webshop and `/admin`, so script injection on any of them reaches the CMS session.
- **Evidence:**
  - `next.config.ts:24-30`: "Deliberately no Content-Security-Policy yet"; `:31-49` sets `nosniff`, `Referrer-Policy` and `Permissions-Policy` on all routes and `X-Frame-Options: DENY` only on `/admin/:path*` (`:44-48`); no `frame-ancestors` anywhere.
  - No `Strict-Transport-Security`, `Cross-Origin-Opener-Policy` or `Cross-Origin-Resource-Policy` in `next.config.ts:31-50`; `poweredByHeader: false` is not set, and Next.js sends `X-Powered-By` by default.
  - One origin for the studio site, webshop and admin (`src/app/layout.tsx:10-19`); session cookie on `Path=/` (`src/lib/cms/session.ts:188`).
  - Known open item: `docs/staging-runbook.md:291`; `docs/booking-runbook.md:536-541`.
- **Status basis:** CSP, COOP and anti-framing gaps observed in config. HSTS and `X-Powered-By` on the deployment are inferred and need `curl -sI` (AT-31); the Vercel edge may add HSTS. Inbound TLS versions and the HTTP redirect (WEB-01) are likewise unprobed (AT-30).
- **Violated controls:** WEB-03, WEB-02, WEB-04.
- **Trade-off the baseline permits:** a nonce needs dynamic rendering of every matched page and turns off static optimisation, ISR and CDN caching (notes under the [Next.js example](../headers-csp.md#example-implementation-nextjs-proxy-with-per-request-nonce)), which conflicts with the repo's preference for cache tags over `force-dynamic` (root `CLAUDE.md` §3, §6). The [Policy](../headers-csp.md#policy) section allows `'sha256-…' 'strict-dynamic'` on static pages ("Pages that must be cached use the hash-based variant"). CMS-backed routes are already `force-dynamic` (`docs/staging-runbook.md:180-181`), so a nonce costs little there; cached pages take the hash variant.
- **Acceptance criteria:**
  1. Inventory and target policy per the [Roll-out procedure](../headers-csp.md#roll-out-procedure): nonce or hash `script-src` with `'strict-dynamic'` and without `'unsafe-inline'` or `'unsafe-eval'`, `object-src 'none'`, `base-uri 'none'`, `form-action 'self'`, `frame-ancestors 'none'` on `/admin` and `'none'` or `'self'` elsewhere, `report-uri` and `report-to`.
  2. Report-Only on staging until the phase 1 exit criteria are met; canary report stored (AT-33).
  3. Enforced; AT-32 passes on one URL per page type (`/`, a CMS page, `/afspraak`, `/admin/login`).
  4. HSTS `max-age` ≥ 31536000 with `includeSubDomains` on the production domain after the [HSTS roll-out](../headers-csp.md#hsts-roll-out); COOP `same-origin`; CORP `same-origin`; `X-Frame-Options` on all HTML; no `X-Powered-By`; AT-31 passes on the same URLs.
  5. AT-30, AT-31 and AT-32 run in `site-health` after every preview and staging deploy.
  6. Moving `/admin` (or the webshop) to its own origin is decided, or the shared origin is accepted in the threat model (D3).
- **Gate: G1** (WEB MUSTs). As for F5, deferring WEB-02, WEB-03 or WEB-04 past G1 needs a signed exception for each.
