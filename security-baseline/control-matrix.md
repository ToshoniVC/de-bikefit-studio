# Control matrix

Canonical control list of security baseline 1.0.0. Topic documents explain defaults and
procedures; when a topic document disagrees with this file, this file wins and the topic document
is a bug. Nothing here states that any control is implemented in any project.

## Profiles

| Profile             | Scope                                                                                             | Typical parts                                                                         |
| ------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| P1 Public site      | Public content and forms; visitors have no accounts                                               | Content pages, contact or booking form, capability links in e-mails (confirm, cancel) |
| P2 Staff/admin      | Authenticated back office or CMS used by staff, contractors or the owner                          | `/admin`, content editing, booking management, user management                        |
| P3 Customer account | End-user accounts holding personal data; payments optional and only through a hosted payment page | Customer portal, order history, saved preferences                                     |
| P4 Non-web service  | API, worker, CLI or scheduled job without a browser UI                                            | Webhook receiver, retention job, import script, machine-to-machine API                |

## Profile selection

Start from the components listed in the threat model ([system description](threat-model.md#system-description))
and apply every rule that matches. Most projects combine profiles (for example P1 + P2 + P4).

| If the project …                                                                                                               | Select |
| ------------------------------------------------------------------------------------------------------------------------------ | ------ |
| serves pages or forms to browsers without login                                                                                | P1     |
| has any login for staff, contractors or the owner, even a single account                                                       | P2     |
| lets visitors create an account or log in with a persistent credential                                                         | P3     |
| runs code without a browser UI that is reachable over the network or touches production data (API, webhook, cron, worker, CLI) | P4     |

Decision rules:

- The applicable level of a control is the strictest value across the selected profiles (M > S > –).
- Capability links sent by e-mail (confirm, cancel) do not make a project P3; WEB-05 and DAT-07
  cover them.
- If the subject of a control does not exist (no uploads, no webhooks), record N/A in the mapping
  with a one-line reason. N/A is not an exception.
- Card numbers never reach our systems: P3 payments use a hosted payment page or redirect.
  Processing card data directly is out of scope of baseline 1.0.0.

## Legend

| Symbol | Meaning                                                                        |
| ------ | ------------------------------------------------------------------------------ |
| M      | MUST for that profile                                                          |
| S      | SHOULD for that profile; a deviation needs a one-line rationale in the mapping |
| –      | Not applicable to that profile                                                 |
| AT-xx  | Acceptance test in [acceptance-tests.md](acceptance-tests.md)                  |

Reference abbreviations: `ASVS 5.0` = OWASP ASVS 5.0.0 requirement ID; `800-63B-4` = NIST SP
800-63B-4 section; `SSDF` = NIST SP 800-218 v1.1 practice; `CS` = OWASP Cheat Sheet. Links and
versions are in [references.md](references.md).

## Risk acceptance

A MUST may be deferred only through a written exception in the project mapping's exceptions
register (format: [adoption-guide.md](adoption-guide.md#exceptions-register)).

| Field                 | Rule                                                                                                |
| --------------------- | --------------------------------------------------------------------------------------------------- |
| Control               | Exactly one control ID                                                                              |
| Reason                | Why the control cannot be met now                                                                   |
| Compensating measures | What reduces the risk meanwhile, or "none" stated explicitly                                        |
| Risk owner            | The project security owner (GOV-01) or a person they delegated in writing; signs with name and date |
| Date                  | Date of signature                                                                                   |
| Expiry                | At most 90 days after the date                                                                      |
| Exit                  | Finding ID or issue link that removes the exception                                                 |

- An expired exception turns the control status back to Missing and fails every gate that needs it.
- Renewal is a new exception with a new date and the reason the fix did not land; nothing extends
  silently.
- Not deferrable: legal duties (breach notification in OPS-05, data-subject requests in DAT-05) and
  rotation of a confirmed leaked secret (DAT-06, SUP-06).
- A SHOULD deviation needs only a one-line rationale in the mapping and has no expiry.
